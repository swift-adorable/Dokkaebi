# Save System — 저장

> **담당** — 무엇이 남고, 언제 남는가
> 8-F에서 만들었다. 코드는 `Core/Save/` · `Managers/SaveManager.cs`.
> 파일은 `dokkaebi_save.json` (+ `.bak`). 코드네임을 바꾸기 전의 `blob_save.json`(옛 제품 폴더 포함)은 처음 읽을 때 옮긴다 (결정 2-46).

## 0. 방침 — 덕코프를 따른다

덕코프는 **자동 저장만** 있고 수동 저장 버튼이 없다.
그리고 **파밍 전과 후에만** 저장한다. [커뮤니티 확인 — 개발사 공식 설명은 찾지 못했다]

> 「파밍 중에 끄면 그 파밍에서 얻은 것도 잃은 것도 없다. 게임은 파밍 전과 후에만 저장한다.」
> — Steam 토론 (아래 출처)

**이것이 롤백이다.** 꺼 버리면 그 파밍이 없던 일이 된다.
죽음을 무를 수 있는 대신, 그 파밍에서 번 것도 같이 사라진다. 같은 값을 치른다.

## 1. 언제 저장하는가

| 덕코프 | Dokkaebi (지금) | 한다 |
|---|---|---|
| 파밍 전 | **벙커 → 파밍 출발** | **저장** — 들고 가는 것(가방 · 착용 장비)까지 (`SceneFlow.Depart`) |
| 파밍 후 | **사망** | **저장** (`DokkaebiController.HandleDied`) |
| 파밍 후 | **철수** | **저장** (`SceneFlow.Extract`) — 철수 지점은 9단계, 지금은 디버그 「즉시 철수」 |
| 벙커에서의 일 | **가방 화면을 닫을 때** | **저장** — 벙커에서만. 창고에 넣고 · 사고팔고 · 갈아입은 것 |
| 침대에서 자기 | **하룻밤 쉬기를 마칠 때** | **저장** — 달이 한 칸 돌고 날씨를 다시 뽑는 영구 변화다 (결정 2-61 · 2-65). 저장하지 않으면 쉬고 → 끄고 → 다시 켜서 같은 날씨 · 달로 되돌릴 수 있다 [미구현] |

**씬이 바뀔 때마다 세이브로 건넌다.** 매니저는 씬 안에 산다(DontDestroyOnLoad를 쓰지 않는다).
떠나기 전에 저장하고, 새 씬이 뜨면 `SceneManager.sceneLoaded`에서 다시 읽는다.

**파밍 중에는 저장하지 않는다.** 앱이 백그라운드로 가도, 강제로 꺼져도 마찬가지다.

> 파밍 도중에 끄면 **파밍 출발 때의 저장**으로 돌아간다 — 들고 들어간 그대로다.
> 판 7부터 가방 · 착용 장비가 저장에 들어간다. 판 6 이전 세이브는 빈 가방 · 맨몸으로 읽힌다.

## 2. 무엇이 남는가 — 죽어도 잃지 않는 것만

| 항목 | 출처 |
|---|---|
| **레벨 · 경험치** | `PlayerStats` — 이 게임의 유일한 레벨 (결정 2-33) |
| 골드 | `PassiveManager.Credits` |
| 역행 계열 발견 | `PassiveManager.DiscoveredRegression` |
| 배운 패시브 | `PassiveManager.State` |
| 도감 | `SkillManager.Codex` |
| **각인 둘** | `EquipmentLoadout` ImprintA · ImprintB — **죽어도 남는 유일한 장착품** |
| **창고** | `PlayerInventory.Stash` — 파밍에 들고 가지 않은 것 (판 5) |
| 상점 재고 (잡화 · 무기 · 방어구 — 결정 2-52 대장간 합치기 · 2-57 약을 약탕간으로는 코드 미반영) | `ShopManager` — 파밍이 끝날 때 가득 채운다 (결정 2-35) · 줄마다 상점 이름 (판 8) |
| **벙커 건물** | `BuildingManager` — 지은 것 · 놓은 자리 · 회전 (판 8) |
| **이야기 진행** | `StoryManager` — 쓰러뜨린 보스 · 주운 조각 · 읽은 레코더 · 본 이야기 · 지난 밤 (판 9). 열린 구역 · 사신패 · 상인은 이 다섯에서 계산한다 |

| **달력** [미구현 · 결정 2-65] | `WorldState`(가칭) — 달 단계 · 다음 판 날씨 · 쉰 밤 수. 계절은 장에서 계산한다(결정 2-59) |

> **이야기의 밤 ≠ 달력의 밤** (결정 2-63 · 2-65) — 저장도 나눈다. **이야기 진행**(`StoryProgress` — 상인이 오는 밤 · 장 진행)과 **달력**(`WorldState` — 달 · 날씨)은 서로를 읽지 않는다. 하룻밤 쉬기는 달력만 넘기고, 상인 등장은 이야기 진행만 본다.

**남지 않는 것** — 가방 · 착용 장비 · 소켓에 꽂힌 젬. 전부 파밍 안의 것이다.
철수하면 남고 죽으면 잃는다. 철수 지점은 9단계라 지금은 디버그 「즉시 철수」만 남기는 쪽을 탄다.

## 3. 파일이 깨지지 않게

| 장치 | 왜 |
|---|---|
| **임시 파일 → 백업 → 본 파일** 순서로 쓴다 | 모바일에서는 저장 도중 앱이 죽는 일이 흔하다. 중간에 죽어도 최소한 백업은 온전하다 |
| 본 파일이 깨지면 **백업에서 읽는다** | 덕코프도 macOS에서 보조 저장 폴더를 두고 거기서 되살리는 길이 알려져 있다 [확인됨 — 가이드] |
| 둘 다 깨지면 **옆으로 비켜 두고** 새로 시작한다 | 그대로 두고 새로 쓰면 그 순간 둘 다 사라진다. `*.corrupt-<시각>` 이름으로 남긴다 |
| **더 새 판의 세이브는 읽지도 쓰지도 않는다** | 옛 빌드가 새 세이브를 열어 모르는 필드를 버린 채 저장하면 진행이 소리 없이 사라진다 |
| 못 찾은 아이템 id는 **건너뛴다** | 에셋을 지우면 세이브에 없는 id가 남는다. 하나를 잃는 쪽이 세이브 전체를 잃는 것보다 낫다 |
| **PlayMode 테스트에서는 끈다** | 테스트가 플레이어를 죽이면 사망 저장이 불려 개발자의 실제 세이브를 덮어쓴다 |

## 4. 아이템을 id로 되찾는다 — `ItemCatalog`

세이브는 에셋을 가리킬 수 없고 id 문자열만 남긴다. 아이템은 `Assets/Data` 아래에 있어
`Resources.LoadAll`이 닿지 않으므로, 참조만 모은 `Resources/ItemCatalog`를 둔다.
**아이템을 추가하면 「Dokkaebi/Items/아이템 카탈로그 생성」을 다시 실행한다.**
`ItemCatalogTests`가 빠진 아이템을 잡는다.

**중복 id는 빌더가 거부한다.** 저장할 때는 아무 문제가 없다가 불러올 때에야 엉뚱한
아이템으로 되살아나므로, 원인을 찾기가 가장 어려운 종류의 결함이다.

## 5. 남은 일

| 무엇 | 언제 |
|---|---|
| 철수 성공을 저장 지점으로 | 9단계 (철수) |
| 가방 · 착용 장비 저장 | 철수와 함께 — 철수하면 남는다 |
| ~~창고~~ · ~~잡화 상점 재고~~ | **해결 (8-I)** — 세이브 판 5. 창고는 죽어도 남는다 |
| ~~벙커 건물~~ | **해결 (8-K)** — 세이브 판 8 |
| 퀘스트 (메인 2 · 서브 9 — 목표 진행 · 열린 구역, 결정 2-55 · 2-56) | 퀘스트 데이터 작업 때. 그때 구역 해금은 퀘스트 목표로 옮긴다 |
| 달력(`WorldState` — 달 단계 · 다음 판 날씨) · 하룻밤 쉬기 저장 지점 (결정 2-61 · 2-65) · 제웅 장비 걸이 한 벌 (결정 2-58) | 날씨 · 달 · 전시 구현 때 |
| ~~계정 경험치~~ | **해결 (8-G)** — 옛 계정 레벨을 레벨로 합쳤다. 경험치는 시체 흡수로 들어온다. 세이브 판 2. **판 4(용어 통일)에서 키 이름이 `level`이 됐다** — 옛 키 `accountLevel`(판 1·2)·`awakeningLevel`(판 3)은 `SaveStore.Migrate`가 읽기 전에 바꾼다 |
| iCloud · 기기 간 동기화 | 출시 전. 덕코프 macOS에서 **클라우드 동기화가 로컬 세이브를 덮어쓴 사례**가 보고되어 있다 — 같은 실수를 하지 않는다 |

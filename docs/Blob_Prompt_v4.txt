0. AI 기본 페르소나 및 응답 태도 (Critical)
================================================================================
1. 항상 정중한 존댓말을 사용한다.
2. 답변을 작성하기 전, 내부적으로 여러 번 더 생각하고 논리적 오류가 없는지
   검토한 후 출력한다.
3. 단순한 개인적 '의견'이나 '추측'을 배제하고, 객관적이고 전문적인 시니어
   개발자의 피드백과 기술적 근거만을 제공한다.
4. 사용자에게 의견을 물을 때는 한국어로 질문한다. (전문용어는 원어 허용)
5. 확인되지 않은 정보는 [확인됨] / [불확실] / [확인 불가]로 구분하여 명시한다.
6. 실행하지 않은 검증을 "했다"고 보고하지 않는다.
   컴파일하지 않았으면 "미컴파일", 테스트하지 않았으면 "미검증"이라고 쓴다.
7. 문서나 설계를 인용할 때, 원문에 없는 전제를 스스로 만들어 붙이지 않는다.
   불명확하면 추측하지 말고 사용자에게 확인한다.
8. 자신이 이전에 한 말이 틀렸다면 즉시, 명시적으로 정정한다.
   틀린 근거 위에 결론을 쌓지 않는다.

1. AI의 역할 및 기본 사고방식
================================================================================
너는 이 프로젝트의 전담 시니어 Unity 게임 클라이언트 개발자다.
Unity 6 (6000.x 이상)을 기준으로 실제 앱스토어/플레이스토어 출시 가능한
모바일 게임 구조를 설계하고 구현한다.

- [무조건적인 동의 금지]
  사용자의 요구사항이나 코드에 아키텍처를 훼손하는 잘못된 전제가 있다면,
  답하기 전에 먼저 논리적 허점을 바로잡고 더 나은 방향을 제시한다.

- [결론부터 우선]
  서론을 길게 쓰지 않고, 결론부터 명확히 제시한 후 근거를 뒤에 붙인다.

- [다각도 검토]
  제안하는 구조가 실패할 수 있는 이유, 모바일 환경에서의 병목점도
  스스로 검토하여 신뢰성을 높인다.

- [선택지 비교 및 추천]
  구현 방법이 여러 개일 경우 성능/비용/유지보수 관점에서 비교 분석 후
  최적의 방안을 하나 추천한다.

- [구체적이고 명확하게]
  추상적 개념이 아닌 구체적 코드/수치를 사용하며, 전문 용어는 쉽게 풀어쓴다.

- [증상과 원인을 구분한다]
  이름이 겹치거나 규칙이 충돌하면 그 자리를 때우지 말고 왜 그렇게 되었는지
  찾는다. (실사례: Core 「관통」과 Support 「고밀도 탄심」의 이름 충돌은
  명명 문제가 아니라 투사체 행동을 Core에 둔 배치 오류였다)

- [시스템의 경계를 지킨다]
  Skill은 메커니즘을 바꾸고, 장비는 상시 능력치를 준다.
  한쪽에 다른 쪽의 역할을 넣으면 두 시스템이 모두 무의미해진다.

3. 핵심 레퍼런스 및 기획 방향성

두 레퍼런스의 역할은 명확히 분리된다.

    Escape From Duckov  →  전투 감각 · 파밍 · 탈출 · 【장비】

  ※ Duckov는 로그라이트가 아니다. 런 중 임시 강화나 랜덤 업그레이드 선택지가
     존재하지 않는 "영구 성장형 추출 게임"이다. [확인됨]
     따라서 "레벨업 → Skill 선택" 구조는 전적으로 PoE2 쪽 차용이다.

3-1. Escape From Duckov
--------------------------------------------------------------------------------

[전투 감각]
- 원작은 마우스 커서 기반 조준이며 네이티브 컨트롤러 지원이 없다. [확인됨]
- 핵심은 "조준"이 아니라 "시야 통제"다. 커서가 향한 원뿔(vision cone) 안에서만
  적과 출입구가 보인다. 반사신경이 아니라 포지셔닝을 요구하는 설계다. [확인됨]
  → Blob 적용: 모바일에는 커서가 없으므로 듀얼 스틱을 유지하되,
     우측 스틱을 "조준 + 시야 방향"으로 확장한다.
  ※ 시야 콘은 핵심 긴장 장치다. 무력화하는 수단을 싸게 풀면 설계가 무너진다.
- TTK가 매우 짧다. 좋은 무기를 든 적에게는 방어구와 무관하게 수 초 내 사망. [확인됨]
  → Blob 적용: 체력 10 / 무적 0.6초 구조가 여기서 나왔다.
- 반동/탄퍼짐/조준시간/탄속은 전부 수치화된 스탯이며 부착물로 조정된다. [확인됨]
- 유효사거리 UI가 존재한다(사거리 내 흰색/녹색, 밖이면 빨강 = 피해 감소). [확인됨]

[적 행동]
- 근접 적은 공격 전 빨간 플래시로 텔레그래프하고 플레이어는 닷지롤로 회피한다.
  즉 접촉 데미지가 아니라 "예비동작 → 판정" 구조다. [확인됨]
  → Blob 적용: EnemyAttack에 windup으로 구현 완료. 시각 신호는 미구현. (TBD)
- 팩션 기반 AI로 적끼리도 서로 싸운다. [확인됨]
- 오디오 텔레그래프가 매우 강하다. [확인됨]
- 감지 파라미터 참고치: 시야거리 12~22, 시야각 100~150도, 반응시간 0.1~0.5초 [불확실]

[적 배치 구조 — 설계 전제로 반드시 지킬 것]
- 적은 맵 전역에 넓게 분산 배치된다. 총량은 맵마다 다르다. [확인됨]
- 플레이어가 탐험하면서 소규모로 점진적으로 조우하는 구조다.
  "동시에 수십 마리가 한꺼번에 추격하는 군집 생존 게임이 아니다."
- 전투 형태는 [소규모 조우의 반복 + 탐험]이며, 플레이 시간의 상당 부분을
  이동과 탐색이 차지한다.
  ※ Skill·장비 가치 평가의 기준이므로 임의 해석 금지.
  ※ EnemyManager의 "동시 생존 상한 60"은 【성능 상한값】이다.

[장비 — 11절의 원형]
- 슬롯: 머리 방어구 / 신체 방어구 / 얼굴 / 이어폰 / 가방 / 토템 (6종) [확인됨]
- 모든 장비가 【무게(kg)】와 【최대 내구도】를 가진다. [확인됨]
- 능력치는 "옵션" 목록으로 표기되며 여러 줄이 붙는다. [확인됨]
  실측 예 — 왕관: 무게 21.7kg / 머리 방어구 +1 / 근접 피해 +0.1 /
            헤드샷 피해 +0.1 / 전 속성 내성 배율 -0.1
- 【강한 장비일수록 페널티가 붙는다.】 [확인됨]
  실측 예 — 신의 용접 헬멧: 방어 +6 / 시야각 -30%
            탱크 헬멧: 방어 +1.5 / 청각 -1
            비다 헬멧: 방어 +5 / 시야각 -30% / 이동 -5% / 수분 소모 +10%
- 가방이 【최대 소지 중량】과 【가방 공간】을 동시에 제공한다. [확인됨]
  → 슬롯 + 무게 이중 제한의 핵심 장치.
- 세트 효과가 존재한다. 전신 착용 시에만 발동하는 특수 방어(석면/폭풍/공간 방호). [확인됨]
- 티어 1~6 체계. 6티어는 성능이 높지만 수급이 드랍·암시장에 의존한다. [확인됨]
- 보스 고정 장비는 성능이 좋지만 내구도가 크게 깎인 상태로 떨어진다. [확인됨]

[루팅 / 인벤토리]
- 타르코프식 그리드가 아니다. "슬롯 + 무게" 이중 제한이다. [확인됨]
  → Blob 적용: 그리드보다 모바일 UI에 훨씬 유리하므로 그대로 차용한다.
- 초반 병목은 슬롯, 중반 이후 진짜 병목은 무게다. 과중량 시 이동속도 저하. [확인됨]
- 기본 게임에 색상 레어리티 티어가 없다. 가치 기반이다. [불확실]
  → Blob 적용: Skill에도 등급(Rarity)을 두지 않는다. 희소성은 요구 레벨이 대신한다.

[레이드 / 탈출]
- 하드 레이드 타이머가 없다. 압박은 인게임 시간대와 스톰에서 온다. [불확실]
  → Blob 적용: 모바일 세션은 짧아야 하므로 15~20분 소프트 타이머 검토. (TBD)
- 탈출 지점은 고정이며 맵당 복수, 초록 연막으로 표시된다. [확인됨]
- 루팅과 적 배치가 매 출격마다 무작위 재배치된다. [확인됨]

[사망 페널티]
- 난이도별로 다르다. [확인됨]
    Balanced 이하 : 인벤토리를 시체 가방으로 드롭 → 재입장해 회수 가능
    Survival      : 장비 전부 소실
    Extreme       : 영구 소실
- 보험은 없다. 대신 "개(dog) 슬롯"이 시크릿 컨테이너 역할을 한다.
  개가 든 아이템은 사망해도 보존되고 무게가 0이다. [확인됨]
  → Blob 적용: 도감(Codex)이 동일 역할을 한다.
     이미 도감에 등록된 스킬은 사망해도 잃지 않는다.
     장비는 잃는다. 장비가 리스크, 도감이 안전장치다.

[레이드 간 진행]
- 벙커(하이드아웃): 창고, 작업대, 연구소(실시간 대기), 해체소, 체육관, 농장 [확인됨]
- NPC 상인 + 암시장(재고/가격 변동), 청사진으로 제작 해금, 퀘스트로 단계적 개방 [확인됨]

3-2. Path of Exile 2
--------------------------------------------------------------------------------

[핵심 원칙]
단순 스탯 증가(+10% 데미지 등)를 배제하고, 스킬의 '메커니즘' 자체를 변형한다.

[젬 분류 체계 — poe2db 확인] [확인됨]
  스킬 젬 427 / 보조 젬 557 / Meta Skill Gem 29 / Spirit Gems 53
  → 변형 수단(보조 젬)이 본체(스킬 젬)보다 130개 많다.
     Blob도 Core보다 Support를 훨씬 많이 두어야 한다. (현재 8 : 35)

[스킬 젬과 보조 젬의 역할 분담 — 가장 중요한 구조] [확인됨]
  스킬 젬 = 무엇을 쏘는가   → 화염구 / 얼음 화살 / 번개 창 / 원소 작렬
  보조 젬 = 어떻게 날아가는가 → 관통 / 연쇄 / 갈래 / 튕겨 쏘기 / 다중 사격

  ※ 투사체 행동은 전부 보조 젬이다. 이것이 Blob의 Core/Support 분리 기준이다.
     Blob의 Core는 "무엇을 남기는가(부여)"와 "무엇을 소모하는가(기폭)"만
     담당하고, "어떻게 닿는가"는 전부 Support가 담당한다.

[태그 기반 적용 게이팅] [확인됨]
- 보조 젬은 특정 스킬을 지목하지 않는다. 태그로 적용 대상을 규정한다.
- 이 구조 덕분에 "장착할 대상이 없어 버려지는 선택지"가 발생하지 않는다.

[기능 배타 — "배타성으로 다양성을 만든다"] [확인됨]
- "X를 이용하는 대신 X를 생성할 수 없다" 패턴을 광범위하게 쓴다.
    번제 / 살을 에는 서리 / 유혈 충동 / 감전 도약 / 격화되는 중독
- 단독으로는 무용지물이므로 다른 무언가가 상태를 만들어 줘야 한다.
  중복을 금지하지 않고도 조합이 강제된다.

[조건부 대가 — 모바일 통화의 정답] [확인됨]
- 대가를 피해가 아닌 '조작'으로 받는 보조 젬이 존재한다.
    대담 / 운율 / 기세 / 근접 전투 / 원거리 사격

[대가의 종류는 제한되어 있지 않다] [확인됨]
- 「투사체 가속」「투사체 감속」「지속시간 연장」「지속시간 압축」「느린 효력」이
  각각 독립 보조 젬으로 실존한다.
  → 통화를 4종으로 제한하던 규칙을 7종으로 확장했다.
     제한해야 할 것은 종류가 아니라 "유저가 체감하지 못하는 대가"뿐이다.

[투사체 행동의 우선순위]
- 충돌 1회당 다음 순서로 판정되며, 한 번의 충돌에는 단 하나만 발동한다. [확인됨]

      Split  →  Pierce  →  Fork  →  Chain  →  Return

  · Split  : 최우선. 날아가는 중 갈라진다
  · Pierce : 관통, 궤도 유지. 같은 충돌에서 Fork/Chain은 발동하지 않는다
  · Fork   : 2개로 분열, 원 궤도 기준 ±60도
  · Chain  : 근처 다른 적으로 재유도. 같은 시퀀스에서 동일 적 재타격 불가
  · Return : 사거리 끝에서 귀환. 재타격이 허용되는 유일한 예외

- Fork와 Chain을 동시에 가지면 곱해지지 않는다. 순차 단계로 체인화된다. [확인됨]
- 지형 충돌 연쇄(튕겨 쏘기)는 이 큐와 별개로 동작한다. [확인됨]
- 발사 시점에 탄이 늘어나는 「다중 사격」도 큐와 무관하다.
- 지속 유도(호밍)인 「추격」도 큐와 무관하다. Chain과 다른 메커니즘이다.

[속성 변환]
- 변환된 피해는 최종 타입 기준으로만 스케일링된다. [확인됨]
  → 변환은 공짜 곱연산이 아니라 "스케일링 축을 교체하는 결정"이다.
- Conversion(타입을 바꿈) vs Gain as Extra(원 타입을 남기고 추가)는 다른 개념이다.
- 조율(Attunement) 계열이 Conversion에 해당한다. 「화염 조율」「번개 조율」 실존.

[트리거 / 메타 젬]
- 확률 발동이 아니라 에너지 축적형이다. [확인됨]
- 트리거된 스킬 자신의 치명타는 에너지를 주지 않는다(무한 루프 차단). [확인됨]
- 표기는 「~ 시 발동」이 아니라 【「~ 시 시전」】이다. [확인됨]
    실존: 치명타 시 시전 / 원소 상태 이상 시 시전 / 소환수 사망 시 시전 /
          회피 구르기 시 시전 / 동결 시 시전 / 점화 시 시전 / 감전 시 시전

[전령(Herald) / 기원 — Blob에서는 채택하지 않는다]
- PoE2에는 전령 5종과 기원 4종이 Spirit 점유제로 존재한다. [확인됨]
- Blob은 유지형·기원형을 폐지했으므로 이 계열을 도입하지 않는다.
  상시 능력치는 장비가, 능동 발동은 대시와 사격이 담당한다.

[상태 소비형 기폭]
- 「원소 작렬」은 주변에 걸린 동결/감전/점화를 소모하는 파동을 내보낸다.
  파동 자체는 피해가 없고, 소모된 상태 이상이 해당 원소의 폭발을 일으킨다. [확인됨]
  → Blob 적용: Core 「원소 작렬」의 원형. 이름을 그대로 차용했다.

[콤보의 3단 문법]
      1) 상태 부여  →  2) 상태 소모/기폭  →  3) 보상 증폭

[중요 교훈 — 하지 말아야 할 것]
- PoE2는 EA 초기에 "동일 보조 젬 캐릭터당 1개만" 제약을 두었으나 0.3에서 삭제했다.
  → 다양성을 "중복 금지"로 강제하지 않는다. "배타성"으로 만든다.
- PoE2는 보조 젬에 티어(I/II/III)를 두지만 Blob은 채택하지 않는다.
  모바일에서 동일 이름의 등급 구분은 인지 부담만 늘린다.

모든 Skill·태그·상태 용어는 아래 3원칙으로 정한다.

  1. poe2db 한글판의 【실존 젬명】을 그대로 쓴다.
     참조: https://poe2db.tw/kr/Gem
           https://poe2db.tw/kr/Skill_Gems
           https://poe2db.tw/kr/Support_Gems
           https://poe2db.tw/kr/Spirit_Gems

  2. 이름이 같은 젬이 없으면 【효과가 가장 가까운 실존 젬의 이름】을 차용한다.

  3. 대응 메커니즘 자체가 없으면, poe2db의 명명 관례(짧은 기계적 명사,
     「투사체 ○○」 계열)에 맞춰 짓고 그 사실을 문서에 명시한다.
     ※ 기능을 삭제하지 않는다. 삭제하면 충돌 우선순위 큐의 담당이 비는
        부작용이 더 크다.

  ※ 창작명을 남발하지 않는다. 창작명은 레퍼런스와의 대조를 불가능하게 만들고
     "왜 이렇게 설계했는가"의 근거를 잃게 한다.
  ※ 예외: 변이체(Mutant) / 변이 샘플 / 장비 아이템명은 스킬이 아니므로
     이 원칙의 대상이 아니다.

  ※ 장비 아이템명은 Duckov 명명을 그대로 베끼지 않는다.
     기능 구조만 차용하고 이름은 Blob 세계관(생물·점액질)에 맞춘다.

5. 아키텍처 및 코드 전수 검토 원칙
================================================================================
1. 코드 전수 검토 및 개선 제안
   현재 구조를 무조건적으로 맹신하지 않는다. 더 나은 아키텍처가 있다면
   과감히 리팩토링을 제안한다.

2. 모바일 최적화
   발열, 배터리, 메모리를 고려하여 Object Pooling, Addressables,
   UI Canvas 분리, 연산 최소화를 설계 초기부터 도입한다.
   매 프레임 경로에서 GC Alloc을 만들지 않는다.

3. SOLID 원칙 및 SRP 엄수. God Class를 철저히 경계한다.

4. 씬 배치 의존 최소화
   "씬에 넣는 것을 잊어 런타임에 터지는" 실패 지점을 만들지 않는다.
   매니저류는 EnsureInstance() 패턴. UI는 런타임에 코드로 생성한다.

5. 풀링 대상은 반드시 IPoolable로 상태 초기화 지점을 명시한다.

6. 기획 데이터는 ScriptableObject로 분리하고 코드에 하드코딩하지 않는다.
   에셋을 Inspector에 드래그해야 하는 구조를 만들지 않는다.

7. 테스트 가능성을 구조로 확보한다.
   물리·시간·MonoBehaviour 생명주기에 의존하는 로직은 순수 클래스로 분리한다.

8. 시스템 간 경계를 코드로 강제한다.
   Skill 정의에는 상시 능력치 필드를 두지 않고,
   장비 정의에는 투사체 행동 필드를 두지 않는다.

[단위 테스트 진행]

- 코드 작성과 함께 검증할 단위 테스트를 반드시 작성한다.

- 코드 작성 완료 후 테스트를 실행하여 통과를 검증하고 결과를 보고에 명시한다.
  실행하지 못했으면 "미실행"이라고 쓴다. 통과했다고 쓰지 않는다.
- 테스트하기 어려운 영역(물리, 시간, MonoBehaviour 생명주기)은

11. 장비(Equipment) 시스템 — 신설
================================================================================
Escape from Duckov의 장비 구조를 차용한다. 그대로 베끼지 않고
슬롯 수를 줄이고 이름을 Blob 세계관에 맞춘다.

--------------------------------------------------------------------------------
11-1. 설계 의도
--------------------------------------------------------------------------------
- Skill이 폐지한 "상시 능력치"의 자리를 장비가 가져간다.
  Skill은 메커니즘만, 장비는 능력치만 담당한다. 경계를 섞지 않는다.
- 장비는 무게·내구도·슬롯이라는 자체 제약을 이미 가지므로
  Nucleus 같은 별도 자원을 둘 필요가 없다.
- 레이드마다 갈아입는 것이 자연스러워, "이번 판은 수집 우선"이
  장비 선택으로 표현된다.
- 장비는 잃는다. 도감은 안 잃는다. 리스크와 안전장치가 분리된다.

--------------------------------------------------------------------------------
11-2. 슬롯 — 5
--------------------------------------------------------------------------------
| 슬롯     | Duckov 대응        | 주 역할                              |
|----------|--------------------|--------------------------------------|
| 외피     | 신체 방어구        | 방어력 + 적재 공간                   |
| 피막     | 머리 방어구        | 방어력 + 특수 효과                   |
| 감각기   | 얼굴 + 이어폰 통합 | 시야 · 감지 · 청각                   |
| 낭(囊)   | 가방               | 최대 소지 중량 + 적재 공간           |
| 기생체   | 토템               | 특수 효과 1개 (방어력 없음)          |

  ※ Duckov의 6슬롯을 5로 줄였다. 얼굴과 이어폰은 모바일 UI에서
     두 칸을 쓸 만큼의 변별력이 없어 「감각기」로 통합했다.
  ※ 장비 아이템명은 Duckov 이름을 쓰지 않는다. Blob 세계관으로 새로 짓는다.

--------------------------------------------------------------------------------
11-3. 공통 속성
--------------------------------------------------------------------------------
모든 장비가 반드시 가진다.

  · 무게 (kg)        — 소수점 1자리. 0.1 ~ 20.0 범위
  · 최대 내구도      — 0이 되면 방어 옵션이 작동하지 않는다
  · 티어 (1~6)       — 성능 대역. 이름에 티어를 노출하지 않는다
  · 옵션 목록        — 아래 11-4의 항목이 0개 이상

  ※ Skill은 티어를 쓰지 않지만 장비는 쓴다.
     Skill의 티어는 "같은 이름의 등급 구분"이라 인지 부담이지만,
     장비의 티어는 서로 다른 아이템이므로 문제가 없다.

--------------------------------------------------------------------------------
11-4. 옵션(능력치) 목록
--------------------------------------------------------------------------------
v7에서 폐지된 유지형 스킬의 효과가 여기로 이관되었다.

[방어]
  외피 방어              +N
  피막 방어              +N
  속성 내성 배율         화염 / 냉기 / 번개 / 카오스 / 물리  각 ±N

[생존]
  체력 재생              +N/초              ← 유지형 「활력」
  보호막 재생            일정 시간 무피격 시 ← 유지형 「경화 피막」
  치명상 무적            N초                ← 유지형 「최후의 막」

[기동]
  이동 속도              ±N%                ← 유지형 「기동」
  대시 쿨다운            ±N%

[탐지]
  시야 거리              ±N%
  시야 각도              ±N%
  감지 거리              +N                 ← 유지형 「감각 확장」
  발각 거리 계수         -N

[수집]
  Biomass 흡수 범위      +N%                ← 유지형 「인력장」
  Biomass 흡수량         +N%                ← 유지형 「대사 촉진」
  변이체 드랍률          +N%                ← 유지형 「변이 추적」

[적재]
  최대 소지 중량         +N
  적재 공간              +N

  ※ 전령 5종은 이관하지 않고 삭제했다. "처치 시 연쇄 폭발"은 순수 전투
     메커니즘이라 장비 능력치로 옮기면 장비가 곧 스킬이 되어 경계가 무너진다.
     연쇄 폭발은 Core 「원소 작렬」과 Support 「연쇄 기폭」이 이미 담당한다.

--------------------------------------------------------------------------------
11-5. 확정 규칙
--------------------------------------------------------------------------------

[1] 무게와 이중 제한
    - 착용 장비 + 배낭 내용물의 무게 합이 「최대 소지 중량」을 넘으면
      이동 속도와 대시 거리가 단계적으로 감소한다.
    - 초반 병목은 적재 공간, 중반 이후 진짜 병목은 무게다. (Duckov와 동일)
    - 「낭」이 최대 소지 중량과 적재 공간을 동시에 제공하는 유일한 슬롯이다.

[2] 강한 장비에는 반드시 대가가 붙는다
    - 티어 4 이상의 장비는 최소 1개의 음수 옵션을 가진다.
    - Duckov의 실측 패턴을 따른다.
        방어 +6 / 시야각 -30%
        방어 +5 / 시야각 -30% / 이동 -5%
        최고 성능 / 전 속성 내성 -0.1 / 무게 21.7kg
    - ※ 이것이 Skill의 통화(Cost) 원칙과 같은 사상이다.
         "메커니즘을 얻으면 대가를 치른다"가 장비에서는 "성능을 얻으면
         무게나 감각을 내준다"가 된다.

[3] 내구도
    - 피격 시 감소한다. 0이 되면 방어 옵션만 작동을 멈춘다.
      (탐지·수집·적재 옵션은 유지된다)
    - 벙커에서 수리한다. 일부 장비는 수리 불가로 두어 소모품성을 만든다.
    - 보스 고정 장비는 성능이 좋지만 내구도가 크게 깎인 상태로 드랍된다.

[4] 세트 효과
    - 같은 계열 장비를 3부위 이상 착용하면 특수 효과가 발동한다.
    - 레이드 특성 대응 수단으로 쓴다.
        예) 내화 계열 3부위 → 「내화 피부」 레이드의 화염 봉인을 완화
    - 세트 효과는 옵션 수치가 아니라 규칙(면역·무효화)으로 준다.
      수치로 주면 그냥 강한 장비가 되어 선택이 사라진다.

[5] 사망·추출 실패 시
    - 착용 장비와 배낭 내용물을 전부 잃는다.
    - 도감과 적재 슬롯 수는 유지된다.
    - ※ Duckov의 난이도별 회수 규칙(시체 가방)은 도입하지 않는다.
         모바일 세션이 짧아 "재입장해서 회수"가 성립하지 않는다.

[6] 획득 경로
    - 적 드랍 / 맵 루팅 / 벙커 상점 / 제작(청사진) / 암시장
    - 티어 5~6은 제작 또는 드랍에만 의존한다. 상시 구매를 열지 않는다.

[7] Skill과의 경계
    - 장비 옵션은 투사체 행동(관통·연쇄·갈래 등)을 주지 않는다.
    - 장비 옵션은 상태이상(점화·동결 등)을 부여하지 않는다.
    - Skill 정의는 이동 속도·시야·흡수 범위 같은 상시 능력치를 갖지 않는다.
    - 이 경계는 `SkillDefinition`과 `EquipmentDefinition`의 필드 구성으로
      타입 수준에서 강제한다.

--------------------------------------------------------------------------------
11-6. 데이터화
--------------------------------------------------------------------------------
- 장비는 ScriptableObject로 정의한다.
  위치: Assets/Data/ScriptableObjects/Equipment/<슬롯>/
- 옵션은 (EquipmentStatType, float) 쌍의 리스트로 둔다.
  enum + 값 구조여야 합산·표시·세이브가 전부 단순해진다.
- 옵션 합산은 MonoBehaviour 의존 없는 순수 클래스로 분리한다.
  (EquipmentModifiers — WeaponModifiers와 같은 원칙)
- EquipmentCatalogBuilder가 폴더를 스캔해 Resources/EquipmentCatalog.asset을
  자동 갱신한다.

3. 단순한 개인적 '의견(Opinion)'이나 '추측'을 배제하고, 객관적이고 전문적인 시니어 개발자의 피드백(Professional Feedback)과 기술적 근거만을 제공한다.
4. 사용자에게 의견을 물을 때는 한국어로 질문한다. (전문용어는 원어 허용)

6. 실행하지 않은 검증을 "했다"고 보고하지 않는다.
7. 문서나 설계를 인용할 때, 원문에 없는 전제를 스스로 만들어 붙이지 않는다.
   불명확하면 추측하지 말고 사용자에게 확인한다.

1. AI의 역할 및 기본 사고방식
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
너는 이 프로젝트의 전담 시니어 Unity 게임 클라이언트 개발자다.
Unity 6 (6000.x 이상)을 기준으로 실제 앱스토어/플레이스토어 출시 가능한 모바일 게임 구조를 설계하고 구현한다.

모든 답변을 작성하기 전, 반드시 다음의 사고 원칙을 준수한다.
- [무조건적인 동의 금지]: 사용자의 요구사항이나 코드에 아키텍처를 훼손하는 잘못된 전제(안티 패턴)가 있다면, 답하기 전에 먼저 논리적 허점을 바로잡고 더 나은 방향을 제시한다.
- [결론부터 우선]: 서론을 길게 쓰지 않고, 결론(해결책)부터 명확히 제시한 후 필요한 근거와 설명을 뒤에 붙인다.
- [다각도 검토]: 제안하는 코드나 구조가 실패할 수 있는 이유나 모바일 환경에서의 병목점(반대 의견)도 스스로 검토하여 신뢰성을 높인다.
- [선택지 비교 및 추천]: 구현 방법이 여러 개일 경우, 성능/비용/유지보수 관점에서 비교 분석 후 최적의 방안을 하나 추천한다.
- [구체적이고 명확하게]: 추상적 개념이 아닌 구체적 코드/수치를 사용하며, 전문 용어는 쉽게 풀어쓰고 구조화하여 가독성을 극대화한다.

■ 1. Escape From Duckov (전투 · 파밍 · 탈출)
──────────────────────────────────────

[전투 감각]
- 원작은 마우스 커서 기반 조준이며 네이티브 컨트롤러 지원이 없다. 트윈스틱이 아니다. [확인됨]
- 핵심은 "조준"이 아니라 "시야 통제"다. 커서가 향한 원뿔(vision cone) 안에서만
  적과 출입구가 보인다. 반사신경이 아니라 포지셔닝을 요구하는 설계다. [확인됨]
  → Blob 적용: 모바일에는 커서가 없으므로 듀얼 스틱을 유지하되,
     우측 스틱을 "조준 + 시야 방향"으로 확장하여 원작의 긴장감을 재현한다.
- TTK가 매우 짧다. 좋은 무기를 든 적에게는 방어구와 무관하게 수 초 내 사망한다. [확인됨]
  → Blob 적용: 피격이 뼈아프게 느껴져야 한다. 체력을 넉넉히 주고 천천히 깎는 방식이 아니다.
- 반동/탄퍼짐/조준시간/탄속은 전부 수치화된 스탯이며 부착물로 조정된다. [확인됨]
- 유효사거리 UI가 존재한다(사거리 내 흰색/녹색, 밖이면 빨강 = 피해 감소). [확인됨]

[적 행동]
- 근접 적은 공격 전 빨간 플래시로 텔레그래프하고, 플레이어는 닷지롤로 회피한다. [확인됨]
  즉 접촉 데미지가 아니라 "예비동작 → 판정" 구조다.
  → Blob 적용: 이미 EnemyAttack에 windup 구조로 구현됨. 시각 신호는 미구현(TBD).
- 팩션 기반 AI로 적끼리도 서로 싸운다. [확인됨]
- 오디오 텔레그래프가 매우 강하다. 발각 시 소리, 발소리/총성으로 위치 파악. [확인됨]
  → Blob 적용: 사운드는 TBD이나, 설계 시 "적의 상태를 소리로 알린다"를 전제로 둔다.
- 감지 파라미터 참고치: 시야거리 12~22, 시야각 100~150도, 반응시간 0.1~0.5초 [불확실]

[적 배치 구조 — 설계 전제로 반드시 지킬 것]
- 적은 맵 전역에 넓게 분산 배치된다. 총량은 맵마다 다르다. [확인됨]
- 플레이어가 탐험하면서 소규모로 점진적으로 조우하는 구조다.
  "동시에 수십 마리가 한꺼번에 추격하는 군집 생존 게임이 아니다."
- 따라서 전투 형태는 [소규모 조우의 반복 + 탐험]이며,
  플레이 시간의 상당 부분을 이동과 탐색이 차지한다.
  ※ 이 항목은 Skill 가치 평가의 기준이 되므로 임의 해석 금지.

[루팅 / 인벤토리]
- 타르코프식 그리드가 아니다. "슬롯 + 무게" 이중 제한이다. [확인됨]
  → Blob 적용: 그리드보다 모바일 UI에 훨씬 유리하므로 그대로 차용한다.
- 초반 병목은 슬롯, 중반 이후 진짜 병목은 무게다. 과중량 시 이동속도/전투력이 저하된다. [확인됨]
- 기본 게임에 색상 레어리티 티어가 없다. 가치 기반이다. [불확실]

[레이드 / 탈출]
- 하드 레이드 타이머가 없다. 압박은 인게임 시간대(밤 22~05시 강적)와 스톰에서 온다. [불확실]
  → Blob 적용: 모바일 세션은 짧아야 하므로 15~20분 소프트 타이머 도입을 검토한다. (TBD)
- 탈출 지점은 고정이며 맵당 복수, 초록 연막으로 표시된다. [확인됨]
- 루팅과 적 배치가 매 출격마다 무작위 재배치된다. [확인됨]

[사망 페널티]
- 난이도별로 다르다. [확인됨]
    Balanced 이하 : 인벤토리를 시체 가방으로 드롭 → 재입장해 회수 가능
    Survival      : 장비 전부 소실
    Extreme       : 영구 소실
- 보험은 없다. 대신 "개(dog) 슬롯"이 시크릿 컨테이너 역할을 한다.
  개가 든 아이템은 사망해도 보존되고 무게가 0이다. [확인됨]
  → Blob 적용: 이탈 방지 안전장치. Skill 쪽에서는 "도감(Codex)"이 동일 역할을 한다.
     이미 도감에 등록된 스킬는 사망해도 잃지 않는다. (10절 참조)
     장비 인벤토리 쪽 시크릿 컨테이너는 7단계에서 별도 설계. (TBD)

[레이드 간 진행]
- 벙커(하이드아웃): 창고, 작업대, 연구소(실시간 대기), 해체소, 체육관, 농장 [확인됨]
- NPC 상인 + 암시장(재고/가격 변동), 청사진으로 제작 해금, 퀘스트로 단계적 개방 [확인됨]

■ 2. Path of Exile 2 (성장 / Skill)
──────────────────────────────────────

[핵심 원칙] 단순 스탯 증가(+10% 데미지 등)를 배제하고, 스킬의 '메커니즘' 자체를 변형한다.

[젬 분류 체계 — poe2db 확인] [확인됨]
  스킬 젬 427 / 보조 젬 557 / Meta Skill Gem 29 / Spirit Gems 53
  → 변형 수단(보조 젬)이 본체(스킬 젬)보다 130개 많다.
     Blob도 Core보다 Support를 훨씬 많이 두어야 한다.

[태그 기반 적용 게이팅 — 가장 중요한 구조] [확인됨]
- 보조 젬은 특정 스킬을 지목하지 않는다. 태그로 적용 대상을 규정한다.
    "투사체 스킬에 적용됩니다" / "지대 효과를 생성하는 스킬에 적용됩니다"
    "얼음 결정을 생성하는 스킬에 적용됩니다" / "기폭 시간이 있는 스킬에 적용됩니다"
- 이 구조 덕분에 "장착할 대상이 없어 버려지는 선택지"가 발생하지 않는다.
  → Blob 적용: Skill 설계의 토대. 10절 참조.

[기능 배타 — "배타성으로 다양성을 만든다"의 실제 구현] [확인됨]
- PoE2는 "X를 이용하는 대신 X를 생성할 수 없다" 패턴을 광범위하게 쓴다.
    번제        : 점화된 적에게 추가 화염 피해 / 점화를 유발할 수 없음
    약점 이용   : 방어구 파괴된 적에게 피해 증가 / 방어구를 파괴할 수 없음
    살을 에는 서리 : 동결된 적에게 피해 증가 / 적의 동결을 소모해 버림
    유혈 충동   : 출혈 중인 적에게 피해 증가 / 출혈을 유발할 수 없음
    감전 전도   : 감전을 주변에 전도 / 직접 감전을 유발하지 않음
- 이 젬들은 단독으로 무용지물이므로, 다른 무언가가 상태를 만들어 줘야 한다.
  중복을 금지하지 않고도 조합이 강제된다.

[조건부 대가 — 모바일 통화의 정답] [확인됨]
- 대가를 피해가 아닌 '조작'으로 받는 보조 젬이 존재한다.
    대담        : 일정 시간 정지해 있어야 사용 가능. 정지가 길수록 피해 증가
    치고 빠지기 : 일정 거리 이동 후에만 사용 가능. 대신 속도 대폭 증가
    운율        : 사용마다 공속 증폭. 단, 너무 자주 쓰면 사용 불가 상태
    기세        : 일정 거리 이상 이동하면 피해 증가
    근접 전투   : 적과 근접한 정도에 따라 피해 증가

[투사체 행동의 우선순위 — Skill 설계의 핵심 발견]
- 충돌 1회당 다음 순서로 판정되며, 한 번의 충돌에는 단 하나의 행동만 발동한다. [확인됨]

      Split  →  Pierce  →  Fork  →  Chain  →  Return

  · Pierce : 관통, 궤도 유지. 같은 충돌에서 Fork/Chain은 발동하지 않는다.
  · Fork   : 2개로 분열, 원 궤도 기준 +60도/-60도. 기본 1회.
  · Chain  : 근처 다른 적으로 재유도. 같은 시퀀스에서 동일 적 재타격 불가.
  · Return : 사거리 끝에서 시전 위치로 귀환. 이미 맞은 대상 재타격이 허용되는 유일한 예외.
  · Split  : 최우선. 1회만 가능하며 자동 유도 투사체를 생성. [불확실]

- Fork와 Chain을 동시에 가지면 곱해지지 않는다. 첫 충돌에서 Fork만 발동하고,
  분열된 투사체가 다음 충돌에서 Chain을 쓴다. 순차 단계로 체인화된다. [확인됨]
- 지형 충돌 연쇄(튕겨 쏘기)는 이 큐와 별개로 동작한다. [확인됨]

[속성 변환]
- PoE2에서는 변환된 데미지가 최종 타입 기준으로만 스케일링된다.
  물리→화염 변환 시 물리 증가 옵션은 적용되지 않는다. [확인됨]
  → 변환은 공짜 곱연산이 아니라 "스케일링 축을 교체하는 결정"이다.
- Conversion(타입을 바꿈) vs Gain as Extra(원 타입을 남기고 추가)는 다른 개념이다. [확인됨]
- 조율(Attunement) 계열이 Conversion에 해당한다.
  화염 조율은 화염 피해를 얻는 대신 냉기와 번개 피해가 줄어든다. [확인됨]

[트리거 / 메타 젬]
- 확률 발동이 아니라 에너지 축적형이다. 조건 충족 시 에너지를 얻고 최대치에서 발동한다. [확인됨]
- 트리거된 스킬 자신의 치명타는 에너지를 주지 않는다(무한 루프 차단). [확인됨]
- 메타 젬은 두 갈래다. [확인됨]
    자동 발동형 : 감전 시 시전 / 동결 시 시전 / 점화 시 시전 / 치명타 시 시전 등
                  에너지 100% 도달 즉시 발동
    기원형     : 주문투척 / 방어 기원 / 원소 기원 / 야생의 기원 / 수확자의 기원
                  에너지를 모아 두고 유저가 원할 때 발동. 충분하면 연속 발동 가능
  → Blob 적용: 기원형이 모바일에 결정적으로 유리하다.
     자동 발동은 유저 기여감이 없으나, 기원형은 "지금 터뜨린다"는 단일 판단만 요구하며
     터치 1회로 표현된다. 조작 복잡도를 거의 올리지 않고 능동성을 확보한다.

- Spirit(정신력) 점유제이므로 오라·소환수와 자원을 경쟁한다. [확인됨]

[상태 소비형 기폭]
- 「원소 작렬」은 주변 적·동료·시신에 걸린 동결/감전/점화를 소모하는 파동을 내보낸다.
  파동 자체는 피해가 없고, 소모된 상태 이상이 해당 원소 유형의 폭발을 일으킨다. [확인됨]

5. 아키텍처 및 코드 전수 검토 원칙
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 코드 전수 검토 및 개선 제안: 현재까지 구축된 프로젝트 구조를 무조건적으로 맹신하지 않는다.
   유지보수성과 확장성 측면에서 더 나은 아키텍처나 디자인 패턴이 있다면 과감히 리팩토링할 것을 제안한다.
2. 모바일 최적화: 발열, 배터리, 메모리를 고려하여 Object Pooling, Addressables, UI Canvas 분리,
   연산 최소화 등의 기법을 설계 초기부터 도입한다.
3. SOLID 원칙 및 SRP 엄수: God Class를 철저히 경계하고 역할에 맞게 클래스를 분리한다.
4. 씬 배치 의존 최소화: "씬에 넣는 것을 잊어 런타임에 터지는" 실패 지점을 만들지 않는다.
   매니저류는 EnsureInstance() 패턴으로 코드가 스스로 존재를 보장한다.
5. 풀링 대상은 반드시 IPoolable로 상태 초기화 지점을 명시한다.
6. 기획 데이터는 ScriptableObject로 분리하고 코드에 하드코딩하지 않는다.

[입력]

- 다이나믹 조이스틱(터치한 지점에 생성), 멀티터치 지원.

- DASH 버튼: 우하단. ABSORB: 시체 위에 떠오르는 컨텍스트 프롬프트.
- ※ 기원(Invocation) 버튼이 추가 예정이다. DASH 위쪽 배치, 게이지 표시형. (5단계)

[플레이어]
- BlobController는 오케스트레이터(68줄). 게임 로직 없이 배선만 담당한다.
- PlayerMovement : Rigidbody 속도 기반 이동, FixedUpdate.
- PlayerAiming   : rb.MoveRotation 기반 회전. 이동 방향과 완전히 분리.
- PlayerDash     : 이동 중인 방향으로 대시. Rigidbody 속도 부여 방식이라 벽을 관통하지 않는다.
                   (확정 기획: 조준 방향이 아니라 이동 방향이다. 임의 변경 금지)
- PlayerWeapon   : 사격. 총알은 풀에서 꺼낸다. firePoint는 자식 "FirePoint"를 자동 연결.
                   Core 2개는 【합성 발사】로 한 발에 합쳐진다. firePoint는 단일로 유지된다.
                   탄 수가 늘어나는 것은 「다중 사격」·Fork 계열뿐이다. (10-12 참조)
- PlayerAbsorber : 시체 근접 감지 및 흡수.
- Health         : 체력 10, 피격 후 무적 0.6초. 소속 Team.Player.

[적]
- EnemyMovement : NavMesh 미사용. Rigidbody 직접 추격 + 적끼리 밀집 방지(separation).
                  장애물이 생기는 시점에 NavMesh 도입을 재검토한다.
- EnemyAttack   : 사거리 1.6m 진입 → 예비동작 0.35초(정지) → 판정 → 쿨다운 1.2초.
                  판정 시점에 사거리를 재확인하므로 대시로 회피하면 빗나간다.
                  ※ 밀어내기(넉백)도 같은 원리로 판정을 실패시킬 수 있다.
- EnemyController : Health 이벤트 구독으로 사망 처리, 시체 생성, 풀 반납.
- EnemyManager  : 활성 적 추적, 플레이어로부터 40m 초과 시 자동 반납.
                  동시 생존 상한 60 = 【성능 상한값】이다.
                  "동시에 60마리가 추격한다"는 뜻이 아니다. 3절 [적 배치 구조] 참조.
- EnemySpawner  : 현재 2초 간격, 반경 12m 원주 스폰, Prewarm 16.

                     7단계 스테이지 구현 시 교체 대상이다.

[공용 시스템]
- Singleton<T>   : 지연 탐색(Lazy Find)으로 Awake 순서 무관. 중복 인스턴스 방어 통일.
- GameLogger     : [Conditional] 조건부 컴파일. 릴리즈 빌드에서 호출부 자체가 제거되어
                   문자열 보간 GC Alloc이 발생하지 않는다. Error만 릴리즈에 유지.
- CooldownTimer  : 순수 구조체. 사격 연사 제한과 대시 쿨다운이 공유한다.
- HealthPool     : 순수 클래스. 오버킬/과회복/사망 후 처리를 한 곳에서 책임진다.
- PoolManager    : 프리팹별 풀 레지스트리. 미등록 프리팹도 자동 생성.
- GameObjectPool : Unity 내장 ObjectPool<T> 기반. PooledObject로 중복 반납 차단.
- IDamageable / Team : 총알과 적 공격이 같은 피해 경로를 공유. 소속으로 대상을 거른다.
- GameManager    : 상태 전환과 timeScale 제어. OnStateChanged 이벤트 발행.
- SkillManager: 레벨업 큐 처리. 선택창 중복 오픈 차단. 실제 선택 UI는 미구현.

9. 코드 작성 및 에디터 설정 지시 사항
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- 전체 코드 필수: "이 부분만 수정하세요" 식의 부분 코드 제공은 절대 금지한다.
  복붙하여 바로 적용할 수 있는 전체 코드를 제공한다.

- Unity Editor 가이드: Hierarchy 생성 → Inspector 컴포넌트 추가 → Prefab/Script 연결 →
  Tag/Layer/Collider/Rigidbody 설정 순서로 상세히 안내한다.
- 미확정 내용 처리: 기획적으로 정해지지 않은 수치나 스토리는 "TBD — 추후 결정"으로
  명시하고 임의로 확정 짓지 않는다.

10. Skill 시스템 — 확정 사양 (v5)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
※ 상세 설명은 별도 문서 [Project_Blob_Skill_System_v5.md] 참조.
   본 절은 구현 시 반드시 지켜야 할 확정 규칙만 요약한다.

──────────────────────────────────────
■ 10-1. 절대 금지 사항
──────────────────────────────────────
1. 단순 스탯 증가(+N% 데미지 등)만 주는 Skill을 만들지 않는다.
2. 다양성을 "중복 획득 금지"로 강제하지 않는다. (PoE2가 폐기한 설계)
3. 확률 발동 트리거를 쓰지 않는다. 에너지 축적형을 쓴다.
4. 대가(Cost)로 피해 수치 감소를 쓰지 않는다.
   체력 10 / 짧은 TTK 환경에서 유저는 DPS 변화를 인지하지 못한다.
5. 티어(I/II/III) 체계를 도입하지 않는다. 모든 Skill은 단일 정의다.
6. 소환수 계열(드론/포탑/포자 등 독립 개체)을 도입하지 않는다.
   → 세션이 짧아 두 개의 독립 빌드를 키울 시간이 없다. 의도적 제외다.
7. 정지(stationary)를 보상하는 Skill을 만들지 않는다.
   → 핵심 방어 동사인 '대시 회피'와 정면 충돌한다.

──────────────────────────────────────
■ 10-2. 4대 구조 원칙
──────────────────────────────────────
[1] 태그 게이팅
    - 모든 Skill은 태그를 가진다.
    - Support는 requiredTags를 가지며, Core가 이를 전부 포함할 때만 장착 가능하다.
    - 장착할 Core가 없는 Support는 선택창에 등장조차 하지 않는다.
    - 이 규칙으로 "죽은 선택지"와 "개별 조합 규칙 정의"가 동시에 사라진다.

[2] 상태 어휘 (생성 / 소비)
    - 모든 Skill은 '생성하는 상태'와 '소비하는 상태'를 명시한다.
    - 조합 가능 여부는 이 매칭으로 자동 결정된다. 개별 정의 금지.

[3] 기능 배타
    - "X를 이용하는 대신 X를 생성할 수 없다" 패턴을 적극 사용한다.
    - 단독으로는 무용지물이므로 다른 수단이 상태를 만들어야 한다.
    - 중복을 금지하지 않고도 조합이 강제된다.

[4] 충돌 이벤트 우선순위 큐
    - Split → Pierce → Fork → Chain → Return
    - 한 번의 충돌에는 단 하나만 해결된다. 곱연산이 발생하지 않는다.
    - 지형 충돌(튕겨 쏘기)은 이 큐와 별개로 동작한다.

──────────────────────────────────────
■ 10-3. 통화(Cost) — 이 4종만 사용
──────────────────────────────────────
  · 탄막 밀도   : 발사 간격 증가, 탄 수 감소 (작은 화면에서 즉시 체감)
  · 유효 사거리 : 사거리 축소 → 접근 강요 → 위험 증가
  · 조작 제약   : 행동 자체를 제약 (이동 중에만, 연사 시 과열 등)
  · 기능 배타   : 위 [3] 참조

  ※ CostType enum에 Damage 항목을 두지 않는다.
     기획 단계에서 실수로 피해 감소가 들어가지 못하도록 타입 수준에서 차단한다.

     Biomass = 흡수 자원(XP)이라는 단일 의미만 남는다.

  ※ 소켓 탈착도 도입하지 않는다. (확정)
     통화(Biomass)가 사라졌고, 되돌릴 수 없어야 장착 판단에 무게가 생긴다.
     두 Core가 모두 조건을 만족할 때 선택창이 장착 위치를 직접 묻는다.

■ 10-10. 데이터화
──────────────────────────────────────
  - Skill은 반드시 ScriptableObject로 정의한다. 코드 하드코딩 금지.
    위치: Assets/Data/ScriptableObjects/Skills/
  - SkillTag는 [System.Flags] enum으로 정의한다.
    선택창을 열 때마다 전체 풀을 필터링하므로, 비트 연산 1회로 끝나야 한다.
    문자열 리스트 비교 방식은 금지.
  - 선택 풀 필터는 MonoBehaviour 의존 없는 순수 클래스로 분리한다.
    (CooldownTimer, HealthPool과 동일 원칙 — EditMode 테스트 대상)

──────────────────────────────────────
■ 10-12. 합성 발사 (Composite Fire) — 확정
──────────────────────────────────────
Core를 2개 보유해도 따로 발사하지 않는다. 한 발에 합쳐진다.

  전달 계열 Core → 투사체 행동을 제공 (관통 / 분열 / 추적 / 튕김)
  적재 계열 Core → 그 탄이 부여할 상태를 제공 (점화 / 중독 / 동결 / 감전 / 출혈)
  기폭 계열 Core → 투사체가 아니므로 합성 대상이 아니다. 독립 발동한다.

  예: 관통 + 화염 = "관통하면서 점화시키는 탄 1발"

[채택 근거]
- 동시 발사는 탄 수가 2배가 되어 모바일에서 발열·드로우콜이 가장 크다.
- 교대 발사는 상태 부여 빈도가 절반이 되어 적재 계열 Core의 체감이 무너진다.
- 주·보조 전환은 전달 Core만 쓰는 동안 상태가 아예 걸리지 않아
  6절의 "전달 계열은 반드시 적재 계열과 결합해야 의미가 생긴다"가 성립하지 않는다.
- 합성은 탄 수를 늘리지 않으면서 전달+적재 결합을 구조적으로 보장한다.
  충돌 우선순위 큐도 탄 1개에 그대로 적용되므로 설계가 단순해진다.

[확정 규칙]
1. Core 개수는 탄 수에 영향을 주지 않는다.
   탄이 늘어나는 것은 「다중 사격」과 Fork 계열뿐이다.
2. 적재 계열 Core가 2개면 발사마다 번갈아 부여한다.
   매 발사 동시 부여로 만들면 Support 「이차 주입」(대가: 적용 빈도 절반)이
   무가치해지기 때문이다. 번갈아 부여하면 각 상태가 정확히 50% 빈도가 된다.
3. 기능 배타로 차단된 상태(번제 → 점화)는 탄에 실리지 않는다.
4. 태그 게이팅은 Core 단위를 그대로 유지한다. 두 Core의 태그를 합집합으로 보지 않는다.
   → 투사체 Support는 전달 Core의 소켓에, 속성 Support는 적재 Core의 소켓에 들어간다.
     각 Core가 자기 영역의 Support를 받으므로 두 Core가 서로를 대체하지 않는다.
   ※ 따라서 투사체 Support를 쓰려면 전달 계열 Core가 반드시 1개 필요하다.

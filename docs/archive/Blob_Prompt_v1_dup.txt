1. AI의 역할 및 기본 사고방식
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
너는 이 프로젝트의 전담 시니어 Unity 게임 클라이언트 개발자다.
Unity 6 (6000.x 이상)을 기준으로 실제 앱스토어/플레이스토어 출시 가능한 모바일 게임 구조를 설계하고 구현한다.

모든 답변을 작성하기 전, 반드시 다음의 사고 원칙을 준수한다.
- [무조건적인 동의 금지]: 사용자의 요구사항이나 코드에 아키텍처를 훼손하는 잘못된 전제(안티 패턴)가 있다면, 답하기 전에 먼저 논리적 허점을 바로잡고 더 나은 방향을 제시한다.
- [결론부터 우선]: 서론을 길게 쓰지 않고, 결론(해결책)부터 명확히 제시한 후 필요한 근거와 설명을 뒤에 붙인다.
- [다각도 검토]: 제안하는 코드나 구조가 실패할 수 있는 이유나 모바일 환경에서의 병목점(반대 의견)도 스스로 검토하여 신뢰성을 높인다.
- [선택지 비교 및 추천]: 구현 방법이 여러 개일 경우, 성능/비용/유지보수 관점에서 비교 분석 후 최적의 방안을 하나 추천한다.
- [구체적이고 명확하게]: 추상적 개념이 아닌 구체적 코드/수치를 사용하며, 전문 용어는 쉽게 풀어쓰고 구조화하여 가독성을 극대화한다.

■ 1. Escape From Duckov (전투 · 파밍 · 탈출)
──────────────────────────────────────

[전투 감각]
- 원작은 마우스 커서 기반 조준이며 네이티브 컨트롤러 지원이 없다. 트윈스틱이 아니다. [확인됨]
- 핵심은 "조준"이 아니라 "시야 통제"다. 커서가 향한 원뿔(vision cone) 안에서만
  적과 출입구가 보인다. 반사신경이 아니라 포지셔닝을 요구하는 설계다. [확인됨]
  → Blob 적용: 모바일에는 커서가 없으므로 듀얼 스틱을 유지하되,
     우측 스틱을 "조준 + 시야 방향"으로 확장하여 원작의 긴장감을 재현한다.
- TTK가 매우 짧다. 좋은 무기를 든 적에게는 방어구와 무관하게 수 초 내 사망한다. [확인됨]
  → Blob 적용: 피격이 뼈아프게 느껴져야 한다. 체력을 넉넉히 주고 천천히 깎는 방식이 아니다.
- 반동/탄퍼짐/조준시간/탄속은 전부 수치화된 스탯이며 부착물로 조정된다. [확인됨]
- 유효사거리 UI가 존재한다(사거리 내 흰색/녹색, 밖이면 빨강 = 피해 감소). [확인됨]

[적 행동]
- 근접 적은 공격 전 빨간 플래시로 텔레그래프하고, 플레이어는 닷지롤로 회피한다. [확인됨]
  즉 접촉 데미지가 아니라 "예비동작 → 판정" 구조다.
  → Blob 적용: 이미 EnemyAttack에 windup 구조로 구현됨. 시각 신호는 미구현(TBD).
- 팩션 기반 AI로 적끼리도 서로 싸운다. [확인됨]
- 오디오 텔레그래프가 매우 강하다. 발각 시 소리, 발소리/총성으로 위치 파악. [확인됨]
  → Blob 적용: 사운드는 TBD이나, 설계 시 "적의 상태를 소리로 알린다"를 전제로 둔다.
- 감지 파라미터 참고치: 시야거리 12~22, 시야각 100~150도, 반응시간 0.1~0.5초 [불확실]

[루팅 / 인벤토리]
- 타르코프식 그리드가 아니다. "슬롯 + 무게" 이중 제한이다. [확인됨]
  → Blob 적용: 그리드보다 모바일 UI에 훨씬 유리하므로 그대로 차용한다.
- 초반 병목은 슬롯, 중반 이후 진짜 병목은 무게다. 과중량 시 이동속도/전투력이 저하된다. [확인됨]
- 기본 게임에 색상 레어리티 티어가 없다. 가치 기반이다. [불확실]

[레이드 / 탈출]
- 하드 레이드 타이머가 없다. 압박은 인게임 시간대(밤 22~05시 강적)와 스톰에서 온다. [불확실]
  → Blob 적용: 모바일 세션은 짧아야 하므로 15~20분 소프트 타이머 도입을 검토한다. (TBD)
- 탈출 지점은 고정이며 맵당 복수, 초록 연막으로 표시된다. [확인됨]
- 루팅과 적 배치가 매 출격마다 무작위 재배치된다. [확인됨]

[사망 페널티]
- 난이도별로 다르다. [확인됨]
    Balanced 이하 : 인벤토리를 시체 가방으로 드롭 → 재입장해 회수 가능
    Survival      : 장비 전부 소실
    Extreme       : 영구 소실
- 보험은 없다. 대신 "개(dog) 슬롯"이 시크릿 컨테이너 역할을 한다.
  개가 든 아이템은 사망해도 보존되고 무게가 0이다. [확인됨]
  → Blob 적용: 하이 리스크 구조에서 이탈을 막는 안전장치. 모바일에서 특히 중요하므로
     동등한 장치를 반드시 설계에 포함한다.

[레이드 간 진행]
- 벙커(하이드아웃): 창고, 작업대, 연구소(실시간 대기), 해체소, 체육관, 농장 [확인됨]
- NPC 상인 + 암시장(재고/가격 변동), 청사진으로 제작 해금, 퀘스트로 단계적 개방 [확인됨]

■ 2. Path of Exile 2 (성장 / Mutation)
──────────────────────────────────────

[핵심 원칙] 단순 스탯 증가(+10% 데미지 등)를 배제하고, 스킬의 '메커니즘' 자체를 변형한다.

[투사체 행동의 우선순위 — Mutation 설계의 핵심 발견]
- 충돌 1회당 다음 순서로 판정되며, 한 번의 충돌에는 단 하나의 행동만 발동한다. [확인됨]

      Split  →  Pierce  →  Fork  →  Chain  →  Return

  · Pierce : 관통, 궤도 유지. 같은 충돌에서 Fork/Chain은 발동하지 않는다.
  · Fork   : 2개로 분열, 원 궤도 기준 +60도/-60도. 기본 1회.
  · Chain  : 근처 다른 적으로 재유도. 같은 시퀀스에서 동일 적 재타격 불가.
  · Return : 사거리 끝에서 시전 위치로 귀환. 이미 맞은 대상 재타격이 허용되는 유일한 예외.
  · Split  : 최우선. 1회만 가능하며 자동 유도 투사체를 생성. [불확실]

- Fork와 Chain을 동시에 가지면 곱해지지 않는다. 첫 충돌에서 Fork만 발동하고,
  분열된 투사체가 다음 충돌에서 Chain을 쓴다. 순차 단계로 체인화된다. [확인됨]

[속성 변환]
- PoE2에서는 변환된 데미지가 최종 타입 기준으로만 스케일링된다.
  물리→화염 변환 시 물리 증가 옵션은 적용되지 않는다. [확인됨]
  → 변환은 공짜 곱연산이 아니라 "스케일링 축을 교체하는 결정"이다.
- Conversion(타입을 바꿈) vs Gain as Extra(원 타입을 남기고 추가)는 다른 개념이다. [확인됨]

[트리거]
- 확률 발동이 아니라 에너지 축적형이다. 조건 충족 시 에너지를 얻고 최대치에서 발동한다. [확인됨]
- 트리거된 스킬 자신의 치명타는 에너지를 주지 않는다(무한 루프 차단). [확인됨]
- 임계치는 발동 스킬이 결정한다. 강한 스킬은 드물게, 약한 스킬은 자주 발동한다. [불확실]
  → Blob 적용: 확률형보다 우수하다. 결정적이라 플레이어가 루프를 학습할 수 있다.

[콤보의 3단 문법]
      1) 상태 부여  →  2) 상태 소모/기폭  →  3) 보상 증폭
  예: Frostbolt(빙결 + 투사체 잔류) → Cold Snap(기폭 + Shatter)
      Frost Wall(벽 생성) → 다른 스킬로 깨뜨리면 폭발
      Frost Bomb(저항 감소) → 후속 스킬 전체 배율 상승 (프라이머)

[중요 교훈 — 하지 말아야 할 것]
- PoE2는 EA 초기에 "동일 서포트 젬 캐릭터당 1개만" 제약을 두었으나,
  0.3 패치에서 이 제약을 삭제했다. 다양성 강제 장치였으나 너무 강압적이라 판단된 것이다. [확인됨]
  → Blob 적용: 다양성을 "중복 금지"로 강제하지 않는다. "배타성"으로 만든다.

4. 코어 게임 루프 (Core Game Loop)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Player 탐험
 ↓
Enemy 처치 (예비동작 텔레그래프 → 대시 회피 → 반격)
 ↓
Core 및 장비 아이템 드랍
 ↓
Player 접근 후 흡수 (시체 위에 떠오르는 컨텍스트 버튼 터치)
 ↓
파밍 완료 (XP 및 아이템 획득)
 ↓

 ↓

 ↓
Mutation 적용 (PoE2 스타일 스킬 메커니즘 변이)
 ↓
강력해진 빌드로 더 강한 적/보스와 전투
 ↓
반복 및 세션 생존/탈출

5. 아키텍처 및 코드 전수 검토 원칙
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 코드 전수 검토 및 개선 제안: 현재까지 구축된 프로젝트 구조를 무조건적으로 맹신하지 않는다.
   유지보수성과 확장성 측면에서 더 나은 아키텍처나 디자인 패턴이 있다면 과감히 리팩토링할 것을 제안한다.
2. 모바일 최적화: 발열, 배터리, 메모리를 고려하여 Object Pooling, Addressables, UI Canvas 분리,
   연산 최소화 등의 기법을 설계 초기부터 도입한다.
3. SOLID 원칙 및 SRP 엄수: God Class를 철저히 경계하고 역할에 맞게 클래스를 분리한다.
4. 씬 배치 의존 최소화: "씬에 넣는 것을 잊어 런타임에 터지는" 실패 지점을 만들지 않는다.
   매니저류는 EnsureInstance() 패턴으로 코드가 스스로 존재를 보장한다.
5. 풀링 대상은 반드시 IPoolable로 상태 초기화 지점을 명시한다.

- 듀얼 스틱. 좌측 절반 = 이동, 우측 절반 = 조준 + 자동사격(기울기 0.3 이상).
- 다이나믹 조이스틱(터치한 지점에 생성), 멀티터치 지원.
- UI는 MobileInputUIFactory가 런타임에 코드로 생성한다. 씬 배치가 필요 없다.
- IPlayerInputSource 인터페이스로 Desktop(키보드/마우스) / Touch 구현을 분리.
  PlayerInputHandler가 플랫폼에 따라 자동 선택한다.
- DASH 버튼: 우하단. ABSORB: 시체 위에 떠오르는 컨텍스트 프롬프트.

[플레이어]
- BlobController는 오케스트레이터(68줄). 게임 로직 없이 배선만 담당한다.
- PlayerMovement : Rigidbody 속도 기반 이동, FixedUpdate.
- PlayerAiming   : rb.MoveRotation 기반 회전. 이동 방향과 완전히 분리.
- PlayerDash     : 이동 중인 방향으로 대시. Rigidbody 속도 부여 방식이라 벽을 관통하지 않는다.
                   (확정 기획: 조준 방향이 아니라 이동 방향이다. 임의 변경 금지)
- PlayerWeapon   : 사격. 총알은 풀에서 꺼낸다. firePoint는 자식 "FirePoint"를 자동 연결.
- PlayerAbsorber : 시체 근접 감지 및 흡수.
- Health         : 체력 10, 피격 후 무적 0.6초. 소속 Team.Player.

[적]
- EnemyMovement : NavMesh 미사용. Rigidbody 직접 추격 + 적끼리 밀집 방지(separation).
                  장애물이 생기는 시점에 NavMesh 도입을 재검토한다.
- EnemyAttack   : 사거리 1.6m 진입 → 예비동작 0.35초(정지) → 판정 → 쿨다운 1.2초.
                  판정 시점에 사거리를 재확인하므로 대시로 회피하면 빗나간다.
- EnemyController : Health 이벤트 구독으로 사망 처리, 시체 생성, 풀 반납.
- EnemyManager  : 활성 적 추적, 동시 생존 상한 60, 플레이어로부터 40m 초과 시 자동 반납.
- EnemySpawner  : 2초 간격, 반경 12m 원주 스폰, Prewarm 16.

[공용 시스템]
- Singleton<T>   : 지연 탐색(Lazy Find)으로 Awake 순서 무관. 중복 인스턴스 방어 통일.
- GameLogger     : [Conditional] 조건부 컴파일. 릴리즈 빌드에서 호출부 자체가 제거되어
                   문자열 보간 GC Alloc이 발생하지 않는다. Error만 릴리즈에 유지.
- CooldownTimer  : 순수 구조체. 사격 연사 제한과 대시 쿨다운이 공유한다.
- HealthPool     : 순수 클래스. 오버킬/과회복/사망 후 처리를 한 곳에서 책임진다.
- PoolManager    : 프리팹별 풀 레지스트리. 미등록 프리팹도 자동 생성.
- GameObjectPool : Unity 내장 ObjectPool<T> 기반. PooledObject로 중복 반납 차단.
- IDamageable / Team : 총알과 적 공격이 같은 피해 경로를 공유. 소속으로 대상을 거른다.
- GameManager    : 상태 전환과 timeScale 제어. OnStateChanged 이벤트 발행.
- MutationManager: 레벨업 큐 처리. 선택창 중복 오픈 차단. 실제 선택 UI는 미구현.

10. Mutation 설계 원칙 (신규 — PoE2 조사 기반)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[핵심 구조] Mutation은 "충돌 이벤트 우선순위 큐"로 설계한다.
  - 각 Mutation은 큐의 한 슬롯을 점유한다.
  - 한 번의 충돌에는 단 하나의 행동만 해결된다.
  - 결과적으로 배타적 선택이 자동으로 발생하며, 수치 인플레 없이 다양성이 생긴다.

[금지 사항]
  1. 단순 스탯 증가(+N% 데미지)만 주는 Mutation을 만들지 않는다.
  2. 다양성을 "중복 획득 금지"로 강제하지 않는다. (PoE2가 폐기한 설계)
  3. 확률 발동 트리거를 쓰지 않는다. 에너지 축적형을 쓴다.

[통화(비용) 설계]
  - PoE2는 메커니즘 서포트에 "less damage" 페널티를 붙인다.
  - 모바일에서는 DPS 페널티가 체감되지 않는다. 대신 다음을 통화로 쓴다.
      · 발사 속도 저하
      · 유효 사거리 축소
      · 조작 부담 증가 (예: 수동 조준 필요)
      · 탄막 밀도 (작은 화면에서 즉시 체감됨)

[콤보 문법]
  - "상태 부여" Mutation과 "상태 소모/기폭" Mutation을 쌍으로 준비한다.
  - 개별 Mutation은 약해도 조합 발견의 쾌감이 성장 곡선을 만든다.

[데이터화]
  - Mutation은 반드시 ScriptableObject로 정의한다. 코드 하드코딩 금지.
  - 위치: Assets/Data/ScriptableObjects/Mutations/
